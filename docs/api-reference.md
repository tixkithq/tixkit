# Tixkit API Reference

Tixkit exposes a JSON HTTP API at `API_BASE_URL` (default `http://localhost:4000` in development). All public/admin endpoints live under the `/v1` prefix. The API is built with Fastify and serves checkout, admin dashboard, scanner, and SDK traffic.

- **Base URL (dev):** `http://localhost:4000/v1`
- **Base URL (prod):** `https://api.<your-domain>/v1`
- **API version:** `2026-01-01` (sent in webhook envelopes; see [Versioning](#versioning) below)
- **OpenAPI schema:** Generated by `@tixkit/openapi`. See `packages/openapi/src/index.ts` for the canonical spec.

## Authentication

Tixkit supports three authenticated principal types plus anonymous buyer routes. The auth middleware picks the mode based on the request shape:

| Mode              | Header(s)                           | Principal `type` | Routes                                               |
| ----------------- | ----------------------------------- | ---------------- | ---------------------------------------------------- |
| Clerk session JWT | `Authorization: Bearer <clerk-jwt>` | `user`           | All authenticated admin/integration routes           |
| API key           | `Authorization: Bearer tk_<key>`    | `api_key`        | All authenticated routes allowed by the key's scopes |
| Scanner device    | `X-Device-Id`, `X-Device-Secret`    | `mobile_device`  | `checkins.read`, `checkins.write` routes             |
| Public buyer      | none                                | none             | `/v1/public/*` and `/v1/checkout/*`                  |

### Clerk session JWT

Issued by Clerk for signed-in admin dashboard users. The API verifies the JWT with `CLERK_SECRET_KEY`, loads the matching `user_profiles` row, and resolves the active organization through the Clerk `org_id` claim or the `X-Tenant-Id` header for users that belong to multiple tenants. Suspended users are rejected.

```bash
curl -X GET http://localhost:4000/v1/me \
  -H "Authorization: Bearer eyJhbGciOi..."
```

### API keys

API keys are long-lived bearer tokens prefixed with `tk_`. They are created in the admin dashboard (Developer settings) or via `POST /v1/api-keys`. The raw key is returned exactly once at creation; the database stores only a SHA-256 hash. Keys carry scopes and optional brand/event bindings:

```bash
curl -X GET http://localhost:4000/v1/events \
  -H "Authorization: Bearer tk_live_01HN..."
```

Revoked (`DELETE /v1/api-keys/:keyId`) or expired keys fail with `401 UNAUTHORIZED`. Last-used timestamps are updated on each authenticated call.

### Scanner devices

Scanner devices authenticate with a `deviceId` and `secret` pair issued via `POST /v1/scanner-devices`. The secret is constant-time compared against the stored hash. Revoked devices fail with `403 FORBIDDEN`.

## Permissions

Every authenticated request resolves to a `Principal` with a list of `Permission` scopes. Required scopes are enforced per route. The permission set is:

```
events.read        events.write
tickets.write
orders.read        orders.write
refunds.write
attendees.read     attendees.write
checkins.read      checkins.write
messages.write
reports.read
settings.write
developers.write
billing.write
```

API keys cannot grant scopes the creating principal does not have. Brand-scoped principals must create brand- or event-scoped credentials; event-scoped principals must create event-scoped credentials. Missing scopes return `403 FORBIDDEN`.

## Pagination

List endpoints use cursor-based pagination with a stable ascending sort by `id` (ULID):

```
GET /v1/events?limit=50&cursor=01HN...
```

| Param    | Type    | Default | Max           |
| -------- | ------- | ------- | ------------- |
| `limit`  | integer | `50`    | `100`         |
| `cursor` | string  | none    | opaque string |

Responses use the page envelope:

```json
{
  "items": [
    /* ... */
  ],
  "nextCursor": "01HN..._next",
  "hasMore": true
}
```

When `hasMore` is `false`, `nextCursor` is `null`. Pass `nextCursor` as the next request's `cursor`.

## Errors

All non-2xx responses use a single envelope:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "limit must be a positive integer",
    "requestId": "req_abc123"
  }
}
```

`requestId` is also returned in the `x-request-id` header-style identifier generated by Fastify. Common error codes:

| HTTP  | `code`                      | Meaning                                                                                                                            |
| ----- | --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `400` | `VALIDATION_ERROR`          | Body/query failed schema validation                                                                                                |
| `400` | `WEBHOOK_SIGNATURE_INVALID` | Webhook signature verification failed                                                                                              |
| `401` | `UNAUTHORIZED`              | Missing/invalid credentials, token verification failed                                                                             |
| `403` | `FORBIDDEN`                 | Authenticated but missing required scope or tenant/org scope                                                                       |
| `404` | `NOT_FOUND`                 | Resource does not exist or is outside the principal's scope                                                                        |
| `409` | `CHECKOUT_CANCELLED`        | Checkout session was cancelled before confirm                                                                                      |
| `402` | `PAYMENT_FAILED`            | Payment intent creation or capture failed                                                                                          |
| `422` | `IDEMPOTENCY_CONFLICT`      | Idempotency key reused with a different payload                                                                                    |
| `429` | `RATE_LIMITED`              | Rate limit exceeded (100 req / min by default; public/webhook routes use the requester IP, authenticated routes use the resolved tenant) |
| `500` | `INTERNAL_ERROR`            | Unexpected server error (logged with `requestId`)                                                                                  |
| `503` | `SERVICE_UNAVAILABLE`       | Temporal/payment intent not yet ready, or webhook secret missing                                                                   |

Validation errors from `ValidationError` include a `fields` array when relevant. Domain errors (`NotFoundError`, `ForbiddenError`, `CheckoutExpiredError`, `WebhookSignatureError`, `IdempotencyConflictError`) surface as 4xx.

## Idempotency

Mutations that start workflows or move money require an `Idempotency-Key` header. The handler stores a `(key, tenant_id)` record with a SHA-256 hash of the request payload:

- Reusing a key with the **same** payload replays the stored response without re-running side effects.
- Reusing a key with a **different** payload returns `422 IDEMPOTENCY_CONFLICT`.
- 5xx responses delete the in-flight record so the caller can retry safely.

Required on these endpoints:

- `POST /v1/checkout/sessions`
- `POST /v1/checkout/sessions/:sessionId/confirm`
- `POST /v1/events/:eventId/box-office/orders`
- `POST /v1/orders/:orderId/refunds`
- `POST /v1/tickets/:ticketId/transfer`
- `POST /v1/check-ins/scan` (recommended), required for `POST /v1/check-ins/sync`, `POST /v1/check-ins/bulk-sync-jobs`, and `PUT /v1/check-ins/bulk-sync-jobs/:jobId/chunks/:sequence`
- `POST /v1/events/:eventId/messages`
- `POST /v1/exports`

```bash
curl -X POST http://localhost:4000/v1/orders/o_abc/refunds \
  -H "Authorization: Bearer tk_..." \
  -H "Idempotency-Key: 7f3c-..." \
  -H "Content-Type: application/json" \
  -d '{"amountCents": 5000, "reason": "buyer request", "voidTickets": true}'
```

## Versioning

- The current API version is `2026-01-01`. Webhook envelopes include this `apiVersion` field (see [Webhook Guide](./webhook-guide.md)).
- The OpenAPI spec at `packages/openapi/src/index.ts` is the contract surface for SDK generation. Breaking changes bump the version and are announced alongside SDK releases.
- URL paths are prefixed with `/v1`. Future incompatible changes will use `/v2` while `/v1` remains supported through the documented deprecation window.

## Public Buyer Routes

These routes are unauthenticated; tenancy is resolved from the published event or brand context.

### `GET /v1/public/events/:eventId`

Returns a published event. Draft/paused/archived events return `404`.

### `GET /v1/public/brands/:brandId`

Returns brand metadata including `theme`, `supportUrl`, `legalUrls`, and `whiteLabel` flag.

### `GET /v1/public/events/:eventId/availability`

Lists public ticket types and live availability. Pass `?products=tt_a,tt_b` to also reveal hidden ticket types by direct-link/product filter.

### `POST /v1/public/events/:eventId/access-code`

Validates an access code or buyer email against locked ticket types. Body:

```json
{
  "ticketTypeIds": ["tt_..."],
  "accessCode": "EARLYBIRD",
  "buyerEmail": "fan@example.com"
}
```

Returns `{ "valid": true, "ticketTypeIds": [...] }` on success or a 400 `VALIDATION_ERROR` describing the failed rule.

### `GET /v1/public/events/:eventId/questions`

Returns buyer and attendee checkout questions for a published event, ordered by `sortOrder`. Only questions for `published` events are returned.

## Checkout Routes

### `POST /v1/checkout/sessions`

Creates a checkout session, reserves inventory, and stores a server-computed quote. Requires `Idempotency-Key`. The client never supplies monetary totals; the server recalculates price, fees, taxes, and discounts from the cart and event configuration.

```json
{
  "eventId": "evt_...",
  "items": [
    { "ticketTypeId": "tt_general", "quantity": 2 },
    { "ticketTypeId": "tt_donation", "quantity": 1, "unitAmountCents": 2500 }
  ],
  "discountCode": "EARLYBIRD",
  "accessCode": "VIP",
  "buyer": { "email": "fan@example.com", "firstName": "..." },
  "successUrl": "https://shop.example.com/thanks",
  "cancelUrl": "https://shop.example.com/cancel",
  "buyerFields": {
    /* answers to buyer-scoped questions */
  },
  "items[].attendeeFields": [
    /* per-attendee answers */
  ]
}
```

Response `201`:

```json
{
  "id": "cs_...",
  "eventId": "evt_...",
  "brandId": "brd_...",
  "status": "open",
  "currency": "USD",
  "quote": {
    /* server-computed totals and line breakdown */
  },
  "expiresAt": "2026-06-25T12:30:00.000Z",
  "successUrl": "...",
  "cancelUrl": "...",
  "orderId": null,
  "clientToken": "cs_tok_..."
}
```

`unitAmountCents` is only accepted for `donation` ticket types. Hidden tickets are purchasable when their IDs are passed explicitly; locked tickets require a valid `accessCode`.

### `GET /v1/checkout/sessions/:sessionId`

Retrieves a session. For non-`completed` sessions, pass `X-Checkout-Session-Token: <clientToken>` to authorize retrieval. For `pending_payment` sessions, you may instead pass `?payment_intent_client_secret=<secret>`.

### `GET /v1/checkout/sessions/:sessionId/wallet-passes`

Lists active Apple Wallet and Google Wallet links for tickets in a checkout session. Completed sessions can be read tokenless from the confirmation page; non-completed sessions require `X-Checkout-Session-Token`. Apple links point to token-protected `.pkpass` downloads. Google links are signed Google Wallet save URLs.

### `GET /v1/wallet-passes/:passId/apple.pkpass`

Downloads a signed Apple Wallet pass. Requires the `token` query parameter from the stored Apple pass URL. Invalid, revoked, or missing-token requests return not found.

### `PATCH /v1/checkout/sessions/:sessionId`

Updates buyer, `successUrl`, or `cancelUrl` on an `open` session. Requires `X-Checkout-Session-Token`.

### `POST /v1/checkout/sessions/:sessionId/confirm`

Starts (or resumes) the checkout workflow. Requires `Idempotency-Key` and `X-Checkout-Session-Token`.

- For **free orders** (`quote.totalCents === 0`), the workflow finalizes the order synchronously and returns `{ order, sessionId, status: "completed" }`.
- For **paid orders**, returns `{ sessionId, status: "pending_payment", paymentIntentId, clientSecret, totalCents, currency }`. The client uses `clientSecret` to confirm payment with Stripe Elements.
- After payment, Stripe's `payment_intent.succeeded` webhook signals the checkout workflow. When the session, hold, and order path can be safely finalized, Tixkit issues tickets, sends confirmation email, and emits the `order.paid` webhook.
- If payment succeeds but the session, hold, or order path cannot be safely finalized, Tixkit treats the payment as orphaned, cancels/voids or refunds it idempotently, does not issue tickets or emit `order.paid`, and requires the buyer to retry from a fresh checkout session.
- Retrying confirm on a `pending_payment` session returns the same active PaymentIntent.

### `POST /v1/events/:eventId/box-office/orders`

Creates an authenticated box-office order for comp, cash, or manual card-not-present tender. Requires `orders.write` and `Idempotency-Key`; tenant, organization, brand, and event scope are checked before inventory is reserved.

The server recalculates the ticket total from the event configuration. `cash` and `manual_card` requests must send an `amountCents` matching that server total. `comp` requests must send `amountCents: 0`; the order is finalized through the same checkout workflow with a zero-total quote. Successful orders store `salesChannel: "box_office"`, the authenticated operator ID, and the tender type.

```json
{
  "tenderType": "cash",
  "amountCents": 2500,
  "buyer": { "email": "door@example.com", "firstName": "Door" },
  "items": [{ "ticketTypeId": "tt_general", "quantity": 1 }]
}
```

Response `201`:

```json
{
  "order": { "id": "ord_...", "salesChannel": "box_office", "tenderType": "cash" },
  "sessionId": "cs_...",
  "status": "completed"
}
```

| `GET`   | `/v1/check-ins/bulk-sync-jobs/:jobId`                        | `checkins.read`   | Poll async offline sync job status                           |
| `GET`   | `/v1/check-ins/bulk-sync-jobs/:jobId/chunks`                 | `checkins.read`   | List async offline sync chunk summaries                      |

Offline sync accepts up to 100,000 scans per request. Scan outcomes: `accepted`, `duplicate`, `not_found`, `already_checked_in`, `invalid_list`, `wrong_event`. Scan logs are persisted with `deviceId`, `scannedAt`, `qrHash`, and `metadata`.

Async bulk sync is for larger offline backlogs. Jobs accept `totalChunks` and optional `totalScans` up to 250,000, chunk uploads accept up to 50,000 scans each, and job/chunk responses return aggregate counters plus bounded redacted error samples rather than per-scan result arrays. Processing waits until every declared chunk is uploaded, then applies the full job in submitted `scannedAt` order with sequence/index tie-breakers. Re-uploading the same chunk with the same payload replays stored chunk state; reusing the sequence with a different payload is rejected.

## Rate Limits

The default Fastify rate-limit plugin applies `100` requests per minute. Public buyer-facing and webhook routes are bucketed by requester IP. Authenticated admin, scanner, and integration routes are bucketed by the resolved tenant after authentication, so one high-volume tenant cannot throttle another tenant sharing the same NAT/proxy address. Production instances require Redis-backed counters; test runs use in-process counters. Authenticated mutation endpoints that start workflows are additionally gated by idempotency. Configure `RATE_LIMIT_MAX` and `RATE_LIMIT_TIME_WINDOW` to raise limits for high-volume scanner or bulk messaging workloads.

## Health

`GET /health` returns `{ "status": "ok", "timestamp": "<iso8601>" }` with no authentication. Use this for load balancer and container health checks.
