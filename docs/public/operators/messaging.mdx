The content editor, sender identity, audience selection, and transport status are separate controls. A saved template is not proof of provider delivery.

## Prepare content

Select the correct brand and event scope. Use the lifecycle or campaign editor appropriate to the message. Preview content with test data and confirm links, unsubscribe/consent behavior, and accessible structure.

## Verify sender readiness

Provider delivery requires the environment's verified email or SMS sender configuration. Local capture behavior can validate rendering without proving provider acceptance. Resolve sender warnings before a live send.

SMTP routes require a TLS connection URL held in the environment variable named by the route's
credential reference. Verify the sender domain and complete a smoke send before activating the
route. SMTP Message-IDs are stable and opaque so an administrator can reconcile an ambiguous
delivery without exposing the job or credential reference.

## Send and verify

Use a limited test audience first. Confirm the dashboard's delivery/capture state and, when authorized, provider evidence. Do not copy recipient lists, message bodies containing personal data, or provider credentials into support reports.

If delivery fails, distinguish invalid sender, provider validation or authentication rejection, rate limiting, provider `5xx`, transport/deadline failure, malformed gateway response, recipient status, and template/render failure before retrying. A timeout after submission can be ambiguous: use the existing delivery/idempotency record and provider evidence instead of creating a second distinct send. Give support only safe correlation identifiers and the provider request ID when available; never include credentials or full message/request/response bodies.
