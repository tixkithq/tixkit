> **Experimental private beta:** the shared identity and delegation contract is public for evaluation. Hosted agent access, managed models, natural-language orchestration, managed prompts, evaluations and managed memory are not generally available. Use only an invited environment and its supplied support channel.

Tixkit agents use explicit principals. An agent does not impersonate its organizer sponsor and cannot write directly to a database. Authorization is evaluated through the existing API and workflow boundaries.

## Current beta surface

API version `2026-07-27`, action protocol `2026-07-22` and plan protocol `2026-07-27` support these sponsor-controlled operations:

- register an agent principal;
- read a principal sponsored by the current user;
- revoke a principal and its active delegations atomically;
- grant and revoke time-bounded event delegations;
- create, inspect, correct, export and delete separately retained organizer memory;
- create and revoke sponsor-bound OAuth clients for active agents;
- exchange client credentials and inspect an explicit, permission-empty agent session;
- prepare and retrieve an immutable `event.publish` action with a server-authoritative dry run;
- persist, inspect and version an immutable multi-step plan over prepared actions;
- issue a short-lived, digest-bound human approval;
- revoke an unconsumed approval through an action-bound, digest-bound lifecycle event; and
- execute one approved `event.publish` action through a durable, idempotent typed operation.

The initial capabilities are `events.read`, `readiness.read`, `events.prepare` and `events.execute`. Consequential execution still requires a typed action, an immutable plan digest and fresh approval. The registration API does not grant unrestricted delegated autonomy, campaign sending or buyer purchasing.

## Authenticate the sponsor

Agent administration accepts only a human bearer principal with tenant-wide `developers.write`. API keys, mobile principals, system principals and users restricted to selected brands or events fail closed. The sponsor must also hold the current event permission implied by every requested capability.

Do not give the agent the sponsor's session. Register the agent while acting as the human sponsor, then use the returned principal identifier in later delegation requests.

## Authenticate the agent

Create a credential with `POST /v1/agent-principals/{id}/oauth-clients`. Its organization is credential-administration ownership only; it does not grant event access. Store the returned `clientSecret` immediately because it is shown once and omitted from idempotent replays. Multiple clients are supported so you can create a replacement before revoking the old credential.

Exchange the client ID and secret at `POST /v1/oauth/token` with `grant_type=client_credentials`. Use HTTP Basic or JSON/form fields, never both and never query parameters. The response is a ten-minute `tk_aat_...` token with fixed `agent.invoke` scope and no refresh token. The JavaScript SDK exposes this server-side flow as `tixkit.agentAuth.exchangeClientCredentials`.

Call `GET /v1/agent/session` with that token to verify the live explicit principal. The session has no organization authority or product permissions. Agent authentication never copies sponsor scopes: current delegation and policy checks remain separate and mandatory for every action. All generic authenticated routes deny agent principals unless their route contract explicitly opts in. Client or principal revocation takes effect on the next request.

## Register an explicit principal

Send a stable caller reference, the agent kind, requested capabilities and maximum autonomy to `POST /v1/agent-principals`. Every mutation requires a unique `Idempotency-Key` of 16–255 characters.

The server derives the tenant, sponsor, protocol version, active state, registration time and tenant-namespaced identifier. Managed Cloud currently accepts `third_party`; Self-Hosted may additionally enable `self_hosted` for a bring-your-own orchestrator.

Store the returned `agt_...` identifier. Reusing an idempotency key with different intent returns a conflict.

## Grant bounded authority

Send the returned principal identifier, capabilities, explicit `event:<id>` scopes and a future expiry to `POST /v1/agent-delegations`. A grant may cover at most 100 unique event scopes and 30 days.

Inside the transaction, Tixkit rechecks the sponsor's current permission grants, accepted organization membership, event ownership and active principal state. The service derives `issuedAt` and `permissionSnapshot`; clients cannot submit either field. A material authorization change requires a new grant or approval.

## Revoke and inspect

The sponsor can inspect only their own principal and can revoke their own principals or delegations. Cross-sponsor resources are returned as not found. Principal revocation cascades to active delegations. Every mutation is idempotent, audited and reauthorizes the human actor before replay.

An explicitly authenticated agent prepares an event publish action through `tixkit.agentActions.prepare` or `POST /v1/agent/actions`. The request contains only the action kind, delegation identifier and event identifier. The server derives identity, sponsor, tenant, resource and policy versions, exact readiness digest, operation and preparation time under a serializable transaction. The resulting action and dry-run evidence are immutable, expire after at most 15 minutes and converge on exact idempotent replay. Cross-agent reads fail closed.

Preparation never authorizes execution. `eligibleForApproval` means only that the live authorization intersection and event readiness passed except for the mandatory approval. A human sponsor with current `events.write` permission issues approval through `tixkit.agentActions.approve` or `POST /v1/agent/actions/{actionId}/approvals`. The request must carry the exact action digest, a unique idempotency key and the explicit confirmation value `approve:<actionId>:<actionDigest>`. Tixkit revalidates the principal, delegation, sponsor, tenant membership, permission, policy, risk, resource version and readiness digest inside the serializable transaction. The resulting approval expires after at most five minutes and cannot be reused for another action.

An exact replay returns the original approval even if authority has since changed, without creating new authority. A new approval request after any material readiness, policy, resource, delegation or permission change fails closed.

The exact human sponsor revokes an unconsumed approval through `tixkit.agentActions.revokeApproval` or `POST /v1/agent/actions/{actionId}/approvals/{approvalId}/revoke`. Revocation remains available after event permission loss, requires the exact action digest and explicit confirmation, converges under exact replay and records one immutable lifecycle event. Cross-sponsor, cross-tenant, changed-binding and consumed-approval attempts fail closed.

The exact authenticated agent executes through `tixkit.agentActions.execute` or `POST /v1/agent/actions/{actionId}/executions`. Send only the approval identifier and exact action digest, with both `Idempotency-Key` and `X-Tixkit-Confirmation` equal to `execute:<actionId>:<approvalId>:<actionDigest>`. Tixkit atomically consumes the unrevoked approval and reserves durable execution evidence. The typed event-publish boundary then rechecks the current principal, delegation, sponsor membership and permission, tenant and risk policy, event version, approval binding and readiness digest before changing the event.

One execution can create at most one recorded product effect. An exact retry after a terminal result returns the same evidence. A retry while another worker holds the execution lease may return `409`; retry it without changing the action, approval or digest. Permanent authorization changes are recorded as a bounded failed execution, while retryable infrastructure faults leave the leased execution resumable. Approval consumption is consequential: a consumed approval cannot be revoked or transferred to another execution.

The exact agent or human sponsor inspects durable execution and its ordered immutable audit history through `tixkit.agentActions.getExecution` or `GET /v1/agent/actions/{actionId}/executions/{executionId}`. Sponsor access remains available after event permission loss for accountability. Cross-tenant, cross-principal, cross-sponsor and cross-action lookups return not found; corrupt or incomplete audit evidence fails closed.

## Persist and inspect an approval-aware plan

After preparing every typed action, the authenticated agent submits the canonical `2026-07-27` plan definition and exact step-to-action bindings through `tixkit.agentPlans.create` or `POST /v1/agent/plans`. The database reloads those actions and rechecks the agent, sponsor, delegation, capabilities, resource scopes, action digests and lifetime. Creation has no product effect and grants no approval.

The exact agent or sponsor reads the immutable definition, bindings and current state through `tixkit.agentPlans.get` or `GET /v1/agent/plans/{planId}`. Advance state with `tixkit.agentPlans.transition` or `POST /v1/agent/plans/{planId}/transitions`. Supply an expected state version, complete next step states, a bounded reason code and an idempotency key. Tixkit owns timestamps and reloads approvals and executions under lock; clients cannot assert their own evidence.

Dependencies, fresh approvals, approval consumption, execution bindings and terminal result digests are validated before the compare-and-swap update. Each accepted transition appends immutable before-and-after state plus canonical, digest-bound actor-authorization evidence. Cross-tenant identifiers remain isolated and material authorization changes fail closed.

## Memory and managed tools

Agent memory is separately retained, scoped, inspectable, correctable, exportable and deletable. Human sponsors manage it through `tixkit.agentMemory` or the `/v1/agent-memory` operations. Namespace ownership and organizer provenance are server-derived. Reads and exports are audited, corrections and deletions are version-aware, and each export contains a checksum over that exact timestamped bundle. Deletion removes content while retaining digest-only audit evidence. The durable maintenance workflow physically erases expired content in bounded, retryable batches. Workspace and event scopes recheck current database authorization; project scope remains unavailable until a durable project resource exists.

Memory content accepts only the typed `organizer_preferences` and `project_context` shapes. Credentials, payment data, buyer data and personal contact data fail closed. Agent retrieval remains delegation-bound through the shared repository and is not a generic HTTP read capability.

Managed messaging may become an agent tool only with consent and suppression evaluation plus exact content and audience approval. Natural-language orchestration and managed memory remain Cloud capabilities; self-hosters may bring an orchestrator through the shared protocol when conformance support is available.
