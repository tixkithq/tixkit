> **Experimental private beta:** the shared identity and delegation contract is public for evaluation. Hosted agent access, managed models, natural-language orchestration, managed prompts, evaluations and managed memory are not generally available. Use only an invited environment and its supplied support channel.

Tixkit agents use explicit principals. An agent does not impersonate its organizer sponsor and cannot write directly to a database. Authorization is evaluated through the existing API and workflow boundaries.

## Current beta surface

API version `2026-08-02`, action protocol `2026-07-22`, plan protocol `2026-07-27` and action-registry contract `2026-08-02` support these sponsor-controlled operations:

- register an agent principal;
- read a principal sponsored by the current user;
- revoke a principal and its active delegations atomically;
- grant and revoke time-bounded event delegations;
- create, inspect, correct, export and delete separately retained organizer memory;
- create and revoke sponsor-bound OAuth clients for active agents;
- exchange client credentials and inspect an explicit, permission-empty agent session;
- read a bounded, version-bound event projection with explicit untrusted-content provenance;
- prepare a normalized, version-bound event update preview without mutating event or media state;
- canonicalize and preview a safe event-page document without mutating product state;
- prepare, freshly approve, execute and exactly replay a normalized, version-bound event update;
- read event readiness through a direct, immutable, digest-bound action result;
- prepare and retrieve an immutable `event.publish` action with a server-authoritative dry run;
- persist, inspect and version an immutable multi-step plan over prepared actions;
- issue a short-lived, digest-bound human approval;
- revoke an unconsumed approval through an action-bound, digest-bound lifecycle event; and
- execute approved `event.publish` and `event.update` actions through durable, idempotent typed operations.

The initial capabilities are `events.read`, `readiness.read`, `events.prepare`, `content.prepare` and `events.execute`. Consequential execution still requires a typed action and fresh approval; plan-supported actions additionally bind approval to an immutable plan digest. The registration API does not grant unrestricted delegated autonomy, campaign sending or buyer purchasing.

## Authenticate the sponsor

Agent administration accepts only a human bearer principal with tenant-wide `developers.write`. API keys, mobile principals, system principals and users restricted to selected brands or events fail closed. The sponsor must also hold the current event permission implied by every requested capability.

Do not give the agent the sponsor's session. Register the agent while acting as the human sponsor, then use the returned principal identifier in later delegation requests.

## Authenticate the agent

Create a credential with `POST /v1/agent-principals/{id}/oauth-clients`. Its organization is credential-administration ownership only; it does not grant event access. Store the returned `clientSecret` immediately because it is shown once and omitted from idempotent replays. Multiple clients are supported so you can create a replacement before revoking the old credential.

Exchange the client ID and secret at `POST /v1/oauth/token` with `grant_type=client_credentials`. Use HTTP Basic or JSON/form fields, never both and never query parameters. The response is a ten-minute `tk_aat_...` token with fixed `agent.invoke` scope and no refresh token. The JavaScript SDK exposes this server-side flow as `tixkit.agentAuth.exchangeClientCredentials`.

Call `GET /v1/agent/session` with that token to verify the live explicit principal. The session has no organization authority or product permissions. Agent authentication never copies sponsor scopes: current delegation and policy checks remain separate and mandatory for every action. All generic authenticated routes deny agent principals unless their route contract explicitly opts in. Client or principal revocation takes effect on the next request.

## Register an explicit principal

Send a stable caller reference, the agent kind, requested capabilities and maximum autonomy to `POST /v1/agent-principals`. Every mutation requires a unique `Idempotency-Key` of 16–255 characters.

The server derives the tenant, sponsor, protocol version, active state, registration time and tenant-namespaced identifier. Managed Cloud currently accepts `third_party`; Self-Hosted may additionally enable `self_hosted` for a bring-your-own orchestrator.

Store the returned `agt_...` identifier. Reusing an idempotency key with different intent returns a conflict.

## Grant bounded authority

Send the returned principal identifier, capabilities, explicit `event:<id>` scopes and a future expiry to `POST /v1/agent-delegations`. A grant may cover at most 100 unique event scopes and 30 days.

Inside the transaction, Tixkit rechecks the sponsor's current permission grants, accepted organization membership, event ownership and active principal state. The service derives `issuedAt` and `permissionSnapshot`; clients cannot submit either field. A material authorization change requires a new grant or approval.

## Revoke and inspect

The sponsor can inspect only their own principal and can revoke their own principals or delegations. Cross-sponsor resources are returned as not found. Principal revocation cascades to active delegations. Every mutation is idempotent, audited and reauthorizes the human actor before replay.

## Read event configuration without approval

An explicitly authenticated agent calls `tixkit.agentActions.readEvent` or `POST /v1/agent/events` with an event identifier, matching delegation grant and idempotency key. The server requires `events.read` in the principal and delegation, exact `event:<id>` scope, current sponsor `events.read` authority and accepted organization membership, plus an allowing `event.read` action/risk policy.

The terminal result is a strict subset of the versioned event: title, description, lifecycle status, currency, timezone, schedule, visibility, capacity and minimum age. It excludes credentials, provider state, buyer/payment data, arbitrary metadata and SEO configuration. `eventSnapshotSha256` binds the projection to the immutable action; `resultSha256` binds the complete timestamped result. `untrustedContentPaths` is exactly `['event.title', 'event.description']`, identifying organizer-authored strings that an orchestrator must treat as data rather than instructions.

Exact replay and `GET /v1/agent/events/{actionId}` recheck the complete current authorization intersection. Revocation, permission or membership loss, scope or policy denial, and resource or policy version drift fail closed. `event.read` cannot enter a plan and cannot create approval, execution or product effects.

## Prepare an event update without approval

An explicitly authenticated agent calls `tixkit.agentActions.prepareEvent` or `POST /v1/agent/event-preparations` with an event identifier, matching delegation, idempotency key and non-empty `changes`. The accepted change object is the complete generic event PATCH surface except `status` and `expectedVersion`; lifecycle status remains confined to its dedicated operations. The server requires `events.prepare` in the principal and delegation, exact event scope, current sponsor `events.write` authority and membership, plus an allowing `event.prepare` action/risk policy.

Resolution uses the same slug, venue, media ownership and normalization rules as organizer PATCH. It validates owned, clean media without renewing its lease and performs no event, venue, upload, approval, execution or plan write. The action payload binds the canonical normalized `changes` and `changePreviewSha256`; the result binds the exact resource version, sorted material fields, before/after projections, observation time and result digest. Every `before.<field>` and `after.<field>` path is declared untrusted because existing and proposed organizer-controlled content is data, never an instruction. Derived organizer-visible effects, such as the venue snapshot resolved from `venueId`, are included in the field set and digest even when the request supplies only the identifier.

Exact replay and `GET /v1/agent/event-preparations/{actionId}` reauthorize the full intersection and return identical persisted evidence. Event or policy version drift, revocation, permission or membership loss, scope denial, slug conflict, foreign venue, foreign or unsafe media, malformed input and persisted-evidence substitution fail closed. `event.prepare` is direct-only and cannot be approved or executed.

## Prepare event-page content without approval

An explicitly authenticated agent calls `tixkit.agentActions.prepareContent` or `POST /v1/agent/content-preparations` with exactly a delegation identifier, event identifier and event-page document. The server requires the `content.prepare` capability, exact event scope, a delegation snapshot and current sponsor authority containing `events:write`, accepted membership, and allowing action/risk policies. It locks and versions the event before deriving any organizer-visible context.

The adapter accepts only channel `event_page` and the safe initial Puck subset: `EventHeader`, `EventDescription`, `Divider`, `Tickets`, `ResaleTickets`, `CheckoutCta` and `BrandFooter`. Input is bounded by canonical bytes, depth, collection size and string size. Unknown fields are stripped against server-owned templates; unsupported components, `CustomEmbed`, populated zones, cyclic values, non-finite numbers and oversized input fail closed. The original is never treated as an instruction. Discovery fields are derived from the same locked event snapshot, validation exposes bounded reason codes rather than raw parser text, and `content` plus `preview.discovery` are explicitly declared untrusted.

The result binds canonical content, derived preview, validation, event version and `contentPreviewSha256` into immutable action and result digests. Exact replay and `GET /v1/agent/content-preparations/{actionId}` reauthorize capability, delegation, sponsor permission, policy and event version before returning identical persisted evidence. The operation writes only action, result and audit evidence: it does not update the event page, uploads, products or other organizer state, cannot enter a plan, and cannot be approved or executed.

## Prepare and execute an event update

An explicitly authenticated agent calls `tixkit.agentActions.prepareEventUpdate` or `POST /v1/agent/event-updates` with the same bounded non-status patch surface. The server requires `events.execute`, exact event scope, an `events:write` delegation snapshot, current sponsor `events.write`, accepted membership and allowing `event.update` policies. It resolves the exact normalized preview without mutation and persists `preview`, `previewSha256`, action digest, authorization evidence and expiry. Exact preparation replay returns identical evidence; `GET /v1/agent/event-updates/{actionId}` supports later inspection.

The human sponsor reviews the complete before/after projection and calls `tixkit.agentActions.approveEventUpdate` or `POST /v1/agent/event-updates/{actionId}/approvals` with confirmation `approve:<actionId>:<actionDigest>`. The explicit agent calls `tixkit.agentActions.executeEventUpdate` or `POST /v1/agent/event-updates/{actionId}/executions` with both idempotency and confirmation set to `execute:<actionId>:<approvalId>:<actionDigest>`. Revocation and evidence retrieval remain on the same dedicated `event-updates` surface. Inside a serializable transaction, Tixkit locks the authoritative state, rechecks the principal, delegation, sponsor, permission, policy, approval, execution fence and resource version, then re-resolves slug, venue and owned-media state from the persisted changes. Any no-op or preview drift invalidates the approval.

One successful transaction applies the optimistic event update and atomically records agent-attributed product audit plus durable effect evidence. The only public result is the event identifier, exactly one incremented resource version and status `updated`. Exact retries converge on that evidence, including recovery after a committed effect. Automatic compensation is unavailable: an inverse change is a new version-bound action requiring fresh approval. `event.update` remains direct-only in `2026-08-02`; it cannot be inserted into a plan.

## Read event readiness without approval

An explicitly authenticated agent calls `tixkit.agentActions.readReadiness` or `POST /v1/agent/readiness` with an event identifier, a matching delegation grant and an idempotency key. The server requires `readiness.read` in the principal capability and delegation, exact `event:<id>` scope, live sponsor `events.read` authority, an `events:read` permission snapshot, and an allowed current tenant action and risk policy.

The response is terminal: it contains an immutable action, action digest, authorization and dry-run evidence, plus a canonical `result` and `resultSha256`. The result reports the current event version, readiness status and snapshot digest, publication state, blocker and warning reason codes, and a server-derived timestamp. Exact replay returns the identical persisted evidence only while the complete current authorization intersection still passes. Principal or delegation revocation, sponsor permission or membership loss, scope or policy denial, and resource or policy version changes deny both replay and `GET /v1/agent/readiness/{actionId}`. The operation never mutates product state, never accepts approval, never creates an execution record and cannot be placed in a plan. Approval or execution attempts against it fail closed.

Use a new idempotency key to observe a later state. A changed event or policy cannot be hidden behind a reused key, and a key reused for different intent returns a conflict.

## Prepare and execute event publication

An explicitly authenticated agent prepares an event publish action through `tixkit.agentActions.prepare` or `POST /v1/agent/actions`. The request contains only the action kind, delegation identifier and event identifier. The server derives identity, sponsor, tenant, resource and policy versions, exact readiness digest, operation and preparation time under a serializable transaction. The resulting action and dry-run evidence are immutable, expire after at most 15 minutes and converge on exact idempotent replay. Cross-agent reads fail closed.

Preparation never authorizes execution. `eligibleForApproval` means only that the live authorization intersection and event readiness passed except for the mandatory approval. A human sponsor with current `events.write` permission issues approval through `tixkit.agentActions.approve` or `POST /v1/agent/actions/{actionId}/approvals`. A standalone request carries the exact action digest and confirmation `approve:<actionId>:<actionDigest>`. Once an action belongs to an authoritative plan, `planSha256` is mandatory and confirmation must be `approve:<actionId>:<actionDigest>:<planSha256>`. Tixkit revalidates the exact plan, step, completed dependencies, principal, delegation, sponsor, tenant membership, permission, policy, risk, resource version and readiness digest inside the serializable transaction. The resulting approval expires after at most five minutes or at plan expiry, whichever occurs first, and cannot be reused for another action or plan.

An exact replay returns the original approval even if authority has since changed, without creating new authority. A new approval request after any material readiness, policy, resource, delegation or permission change fails closed.

The exact human sponsor revokes an unconsumed approval through `tixkit.agentActions.revokeApproval` or `POST /v1/agent/actions/{actionId}/approvals/{approvalId}/revoke`. Revocation remains available after event permission loss, requires the exact action digest and explicit confirmation, converges under exact replay and records one immutable lifecycle event. Cross-sponsor, cross-tenant, changed-binding and consumed-approval attempts fail closed.

The exact authenticated agent executes through `tixkit.agentActions.execute` or `POST /v1/agent/actions/{actionId}/executions`. Send only the approval identifier and exact action digest, with both `Idempotency-Key` and `X-Tixkit-Confirmation` equal to `execute:<actionId>:<approvalId>:<actionDigest>`. Tixkit atomically consumes the unrevoked approval and reserves durable execution evidence. Planned execution is persisted with the plan digest. The typed event-publish boundary locks and rechecks the current plan and step alongside the principal, delegation, sponsor membership and permission, tenant and risk policy, event version, approval binding and readiness digest before changing the event. Cancellation wins before reservation or effect application; once an execution exists, cancellation is rejected rather than claiming that a consequential effect was stopped.

One execution can create at most one recorded product effect. An exact retry after a terminal result returns the same evidence. A retry while another worker holds the execution lease may return `409`; retry it without changing the action, approval or digest. Permanent authorization changes are recorded as a bounded failed execution, while retryable infrastructure faults leave the leased execution resumable. Approval consumption is consequential: a consumed approval cannot be revoked or transferred to another execution.

The exact agent or human sponsor inspects durable execution and its ordered immutable audit history through `tixkit.agentActions.getExecution` or `GET /v1/agent/actions/{actionId}/executions/{executionId}`. Sponsor access remains available after event permission loss for accountability. Cross-tenant, cross-principal, cross-sponsor and cross-action lookups return not found; corrupt or incomplete audit evidence fails closed.

## Persist and inspect an approval-aware plan

After preparing every plan-supported typed action, the authenticated agent submits the canonical `2026-07-27` plan definition and exact step-to-action bindings through `tixkit.agentPlans.create` or `POST /v1/agent/plans`. The database reloads those actions and rechecks the agent, sponsor, delegation, capabilities, resource scopes, action digests and lifetime. Creation has no product effect and grants no approval. The `2026-08-02` registry marks `event.read`, `readiness.read`, `event.prepare`, `content.prepare` and `event.update` as direct-only, so they are evidence or standalone approved actions rather than plan steps.

The exact agent or sponsor reads the immutable definition, bindings and current state through `tixkit.agentPlans.get` or `GET /v1/agent/plans/{planId}`. Advance state with `tixkit.agentPlans.transition` or `POST /v1/agent/plans/{planId}/transitions`. Supply an expected state version, complete next step states, a bounded reason code and an idempotency key. Tixkit owns timestamps and reloads approvals and executions under lock; clients cannot assert their own evidence.

Dependencies, fresh approvals, approval consumption, execution bindings and terminal result digests are validated before the compare-and-swap update. Each accepted transition appends immutable before-and-after state plus canonical, digest-bound actor-authorization evidence. Cross-tenant identifiers remain isolated and material authorization changes fail closed.

## Memory and managed tools

Agent memory is separately retained, scoped, inspectable, correctable, exportable and deletable. Human sponsors manage it through `tixkit.agentMemory` or the `/v1/agent-memory` operations. Namespace ownership and organizer provenance are server-derived. Reads and exports are audited, corrections and deletions are version-aware, and each export contains a checksum over that exact timestamped bundle. Deletion removes content while retaining digest-only audit evidence. The durable maintenance workflow physically erases expired content in bounded, retryable batches. Workspace and event scopes recheck current database authorization; project scope remains unavailable until a durable project resource exists.

Memory content accepts only the typed `organizer_preferences` and `project_context` shapes. Credentials, payment data, buyer data and personal contact data fail closed. Agent retrieval remains delegation-bound through the shared repository and is not a generic HTTP read capability.

Managed messaging may become an agent tool only with consent and suppression evaluation plus exact content and audience approval. Natural-language orchestration and managed memory remain Cloud capabilities; self-hosters may bring an orchestrator through the shared protocol.

## Prove an orchestrator against the shared contract

The public `@tixkit/contract-tests` source package includes a live `agent-platform` profile for third-party and Self-Hosted orchestrators. It verifies direct event reads, event preparation and safe content preparation, rejection of content approval/execution, an approval-bound event update with exact execution replay, readiness evidence and the plan-bound `event.publish` golden path: client-credential authentication, explicit agent identity, version/digest and untrusted-content binding, typed action preparation, fresh sponsor approval, idempotent execution, canonical plan persistence, terminal plan state and audit evidence against one API environment. It does not claim hosted availability or cover the separate memory and revocation contracts.

This profile prepares event-page content, changes the event title and description, then publishes it. Use only an isolated private-beta or Self-Hosted test tenant and an unpublished disposable event that is ready to publish. Never run it against a production event. The sponsor must own the agent and retain `events.read` and `events.write`; the agent delegation must grant `events.read`, `readiness.read`, `events.prepare`, `content.prepare` and `events.execute` for that exact event.

Install the runner and create a fixture containing identifiers and environment-variable names, never credential values:

```sh
npm install --save-dev @tixkit/contract-tests
```
