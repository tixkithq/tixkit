Protect buyers and preserve evidence before changing state. Record severity, start time, affected environment, safe correlation identifiers, and the current mitigation owner. Never paste secrets, credentials, customer payloads, or raw database dumps into the incident record.

This Self-Hosted runbook is not a Tixkit Cloud status page or public managed incident history. Managed Cloud is not generally available, and no public managed incident surface is offered.

## General triage

1. Confirm scope by tenant/organization/brand/event without crossing isolation boundaries.
2. Check recent deploys, migrations, provider status, API/worker health, task-queue lag, database, Redis, and storage.
3. Stop or rate-limit the unsafe side effect while preserving read access where possible.
4. Choose rollback, forward repair, provider reconciliation, or restore based on tested compatibility.

## Payment or refund disagreement

Reconcile Tixkit order/refund records, workflow history, and provider references. Do not issue a second refund or capture before confirming the first attempt. Use the supported compensation/repair path and verify customer-facing status afterward.

## Webhook dead letters

Confirm endpoint reachability and signature verification, then fix receiver idempotency before replay. Replay a bounded event set and verify event IDs at the receiver.

## Outbound provider failure

Classify the failure before replaying work: transport or deadline, `429` rate limit, selected `5xx`, malformed/non-JSON gateway response, permanent provider `4xx`, or customer/recipient decline. Correlate dependency, operation, status, duration, retry classification, Tixkit request/workflow ID, and a safe provider request ID. Respect `Retry-After` and the owning workflow's retry policy; stop retry multiplication if both layers are repeating the same operation.

For a timeout after a side-effecting payment, refund, or message request, assume the result is ambiguous. Reconcile with the same idempotency key or provider reference before attempting another side effect. Preserve bounded redacted diagnostics, but do not attach authorization headers, client secrets, webhook signatures, full provider bodies, or customer payloads to the incident.

## Stuck checkout or export

Inspect the durable workflow/activity and dependency status. Restore workers/storage/providers, retry through supported operations, and verify order/inventory or export artifact state. Avoid creating many duplicate jobs.

## Recovery validation

Run targeted health and golden-path checks, confirm alerts clear for the right reason, communicate residual impact, and capture follow-up changes with owners. Rehearse restore when integrity is uncertain.
