Generate a unique `Idempotency-Key` for one logical mutation and retain it until that mutation reaches a known result.

```http
POST /v1/orders/ord_example/refunds HTTP/1.1
Authorization: Bearer $TIXKIT_API_KEY
Idempotency-Key: 018f-example-logical-operation
Content-Type: application/json
```

Reusing a key with the same payload can replay the stored result without repeating side effects. Reusing it with a different payload returns `IDEMPOTENCY_CONFLICT`. Never use one constant key for all requests.

After a timeout, query the resource or retry with the same key and identical payload. Do not generate a new key until you know the original operation should be a separate side effect.
