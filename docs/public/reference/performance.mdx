Performance claims require measured evidence. Repository budgets cover the configured application routes and documentation-specific search/reference behavior.

```bash
bun run check:performance-budgets
bun run check:lighthouse-budgets
```

The docs architecture budgets compressed search bootstrap and shards, search-open interaction, initial JavaScript, layout stability, content paint, and API-reference loading. The OpenAPI JSON is downloadable but is not loaded on ordinary guide pages; the local search index loads only after search intent.

## Real-user monitoring contract

Checkout and hosted event pages send only LCP, INP and CLS to `POST /v1/public/rum`. The strict, versioned application payload contains a bounded surface name, a bounded metric name and a finite bounded value; URL, path, referrer, host, event, tenant, user, session, visitor, request and arbitrary-label fields are rejected. Delivery omits credentials, runs asynchronously without retry and cannot block checkout. The API limits the body to 512 bytes, applies a tighter public rate limit, writes no database or object record and exposes only fixed-cardinality Prometheus histograms. Network services can still observe transport metadata, so operators must apply their privacy and retention policy to proxy and application access logs.

Production-profile alert definitions evaluate 15-minute p75 values after at least 100 samples: LCP ≤ 2.5 seconds, INP ≤ 0.2 seconds and CLS ≤ 0.1. These public samples are untrusted operational signals, not product analytics or release evidence. The repository proves the local collector, browser adapter, metric contract and rendered alert expressions; it does not claim representative production traffic, abuse resistance, privacy or retention approval, a routed alert, budget attainment, or an SLA/SLO.

## Payment-provider service signals

Every dispatched payment-provider operation attempt is normalized at the provider-client boundary as `success`, `decline`, `caller_cancelled` or `platform_failure`. Stripe card errors and HTTP 402 payment rejections are declines. Invalid requests, configuration failures, timeouts, transport failures, rate limits, server failures, malformed responses and unknown failures are platform failures. Only an explicit caller abort is caller cancellation; API status or error text does not perform this classification.

Workers count callbacks from every attempt, including calls repeated by Temporal activity retries, in a fixed-cardinality metric with only `surface="payment"` and the bounded outcome. The Production chart defaults to a 15-minute window and 100 eligible samples. Platform failure is measured as `platform_failure / (success + platform_failure)` with a 2% threshold. Declines are separately measured as `decline / (success + decline)` with a 15% threshold. Caller cancellations are outside both ratios.

Tests prove the local classifier, immutable and failure-isolated callback, bounded metric labels and rendered PromQL. These defaults are not a production SLA/SLO, provider baseline or alert-delivery claim. Operators need retained production volume, routed-alert proof and an approved objective before making such a claim.

Trusted database regression jobs retain three fresh-process samples and a deterministic aggregate for PostgreSQL and MySQL. The aggregate binds the commit, runner label, pinned database image, workload, complete metric set, and checksums, and reports per-metric min, median, p95, and max. Every individual sample must remain inside the absolute budget.

These checksums provide integrity detection, not a producer signature or independent authenticity proof. Authenticity depends on the trusted workflow and retained-artifact controls.

This evidence detects regressions for the committed workload on the trusted runner. It does not prove deployment capacity, soak stability, fault behavior, or real-user experience. Historical median comparison requires a compatible predecessor from the same runner, database, workload and metric set plus the committed regression threshold; the compared Git revisions are expected to differ.

The nightly workflow has a bounded cross-revision trend contract. Its committed configuration fixes metric directions, maximum regression, history length and archive limits. The generator verifies and re-derives the raw metrics, sealed samples, aggregate and scenario result before producing checksummed JSON and a static HTML view. A first compatible run is only a candidate and explicitly makes no trend claim. Prior artifacts come from a bounded set of default-branch workflow runs and are retained workflow artifacts, not immutable public releases.

The trend implementation is locally validated, but no hosted trend artifact is claimed until the protected workflow actually completes. A future passing artifact remains limited to its controlled single-host workload; it is not Production or Compact capacity, RUM, provider, or service-SLO evidence.

The scheduled trusted workflow also runs committed PostgreSQL and MySQL regression scenarios. Each scenario requires four bounded bursts spaced across 30 minutes and binds the revision, trusted-runner label, pinned database image, workload and explicit `trusted-single-host-regression` profile. It fails closed on incomplete duration, missing or extra metrics, source-metrics mismatch, identity drift, timeout, invalid or incompatible retained baseline, median regression and evidence-directory reuse. All evidence produced before a failure plus a bounded failure record is uploaded; raw metrics, sealed samples and aggregates exist only when execution reaches those stages.

This scheduled evidence improves regression ownership but is not soak evidence and is not a supported-profile capacity envelope. Compatible runs can feed the bounded trend artifact, but the single trusted host is not the Production Kubernetes profile, retained GitHub artifacts are not immutable publication, and these runs do not establish production fault behavior, RUM or general long-term production trend availability.

The separate weekly/manual capacity workflow characterizes the controlled trusted runner label with serial PostgreSQL and MySQL profiles, four increasing concurrency points and three fresh-process samples per point. It classifies only inventory exhaustion with zero availability as expected decline; another rejection is a platform failure. It records both total request and successful-reservation throughput, and saturation uses only successful-reservation throughput and latency so fast sold-out responses cannot improve the result. Any sample p95 or platform-failure breach, or the first median successful-throughput gain below its threshold, establishes saturation. It emits a bounded claim only when saturation follows a lower publishable point; no observed saturation means no capacity claim.

That artifact's literal scope is `trusted-single-host-capacity-characterization`. It explicitly denies Production, Cloud, Compact and general capacity. Git/config/workload/raw hashes are checksums, not signatures, and workflow retention is not public immutable evidence. Before running a sample or creating an output directory, the workflow compares a topology-sensitive, privacy-minimized hardware fingerprint with the expected digest. The evidence retains only the fingerprint contract version and digest, not hostnames, raw CPU model strings or other machine identifiers. The expected fingerprint digest is configured outside the repository. A missing or mismatched digest fails closed, so runner remapping or hardware drift requires explicit review and reconfiguration; this identity check does not turn a trusted-host result into Production-profile capacity evidence.

A failed workflow uploads a checksummed diagnostic marker with phase and step outcomes. It binds the config checksum only after checkout succeeds, is not schema-validated capacity evidence and cannot carry a capacity claim.

The separate trusted-host database dependency fault workflow is an explicitly authorized destructive test on the dedicated runner. It stops the exact digest-pinned PostgreSQL or MySQL service container, releases 64 stable reservation identities only after the stop is observed, requires 64 classified dependency failures and zero durable holds, restores and health-checks the same container, waits independently for host-side query reachability, then replays the exact identity set. Passing evidence requires 64 successful reservations, one active hold per identity, no partial or unknown hold state and no oversell. The runner attempts and verifies restoration before surfacing a primary protocol failure.

Evidence binds injection/restoration ordering and durations, the recovery threshold, normalized original/replay identity-set hashes, all fault/replay outcome categories, reconciliation, revision, config and workload. Its literal scope is `trusted-single-host-database-dependency-fault`; it is not Production availability or fault-tolerance, Cloud or Compact availability, provider or Temporal resilience, or an SLA/RTO claim. Those systems are not exercised, checksums are not signatures, retained artifacts are not immutable publication, and the committed workflow alone is not hosted proof.

The separate trusted Temporal dependency-fault workflow starts 16 concurrent ordered migration workflows against digest-pinned Temporal 1.24 with a separate PostgreSQL 16 persistence service. It stops only the Temporal service after every workflow enters its first idempotent activity, then restores the same container and waits for Docker health plus host-side reachability. Success requires every original workflow/run identity to complete, every 13-stage order and history checksum to remain bound, reconciliation/completion logical effects to occur once, failure effects to remain zero, and every history to replay without nondeterminism. Activity attempts may exceed logical effects after an unavailable completion acknowledgement.

Its literal scope is `trusted-single-host-temporal-service-dependency-fault`. It is not Production, Cloud, Compact, multi-node or managed Temporal availability; database or migration-data correctness; provider, webhook or scanner resilience; exactly-once external side effects; capacity, soak, SLA, RTO or RPO proof. Checksums are not signatures, retained workflow artifacts are not immutable publication, and the committed contract is not hosted evidence.

The weekly/manual trusted-host soak workflow continuously repeats the unchanged integration workload for at least four hours on PostgreSQL and MySQL in serial. It requires at least 24 complete fresh-process iterations, no more than five seconds between one completion and the next spawn, every absolute budget to pass, and no missing, partial, timed-out or unclassified result. Component tests assemble combined metrics in a private staging path; the runner validates them and promotes the final bytes once into create-only retained raw evidence before starting another child. It binds and orders every raw metric and sealed-sample checksum, records whole-run distributions, and limits adverse median drift between the first and last six iterations to 15%.

That artifact's literal scope is `trusted-single-host-continuous-integration-soak`. It is repeated system/database workload evidence, not same-process memory-leak proof. It explicitly denies Production, Cloud or Compact stability, provider or Temporal resilience, capacity, RUM, SLA/SLO attainment, and immutable or public evidence. A committed executable workflow is not a hosted soak result; a protected run must actually complete before retained evidence exists.

Browser measurements use the lockfile-pinned Playwright Chromium installed on the trusted runner by the repository runtime installer. Record environment, commit, viewport, browser, sample count, and artifact when reporting a regression. Do not convert an unmeasured target into a success claim.
