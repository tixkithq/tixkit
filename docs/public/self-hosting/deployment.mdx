Deploy immutable artifacts built from one reviewed commit. The API, worker, OpenAPI reference, SDK compatibility statements, dashboard, checkout, and docs must describe the same contract.

Use the [Compact profile](/self-hosting/compact) for a complete supported single-host evaluation or smaller installation. Use the Production profile and externally operated backing services for high availability and independent scaling.

Follow the dedicated [Production profile runbook](/self-hosting/production) for compatibility, sizing, secret, migration, network, observability, and recovery gates.

The Production chart is `infra/helm/tixkit` with `values-production.yaml`. It intentionally refuses placeholder image digests, bundled datastores, unrestricted network CIDRs, automatic migration hooks, missing observability, and incomplete ExternalSecret mappings. Supply release-manifest image digests and environment-specific ingress, database, and service egress ranges; do not weaken these checks with a copied evaluation file.

For External Secrets, reconcile the `ExternalSecret` and wait for its target Secret before running `infra/scripts/run-helm-migration.sh`. The runner validates the chart-derived key inventory, acquires an atomic migration lock, applies the release-scoped database egress policy, creates a uniquely named bounded Job, waits for completion, and prints current logs. It fails rather than reusing a completed Job or overlapping another migration. This local runner evidence does not replace a production-like install, upgrade, rollback, and recovery rehearsal.

Offline browser check-in requires `OFFLINE_MANIFEST_ACTIVE_KEY_ID` and `OFFLINE_MANIFEST_SIGNING_PRIVATE_KEYS_JSON`. The registry is a non-empty JSON array of P-256 private keys with unique `keyId`, PKCS#8 PEM `privateKeyPem`, and canonical UTC `notBefore`/`notAfter` instants. The chart isolates these values in the API-only `<release>-tixkit-manifest` Secret; existing-secret installations must create that separate Secret, and External Secrets mode creates a separate target automatically. Keep the active key valid for the complete 24-hour manifest lifetime.

Generate the first registry on an authorized administrative workstation. This command refuses to overwrite an existing file and writes it with mode `0600`; transfer the file directly into your secret manager and remove the workstation copy after verification.

```bash
umask 077
node --input-type=module <<'NODE'
import { generateKeyPairSync } from 'node:crypto';
import { writeFileSync } from 'node:fs';

const keyId = `manifest-${new Date().toISOString().slice(0, 10)}`;
const privateKeyPem = generateKeyPairSync('ec', { namedCurve: 'P-256' }).privateKey.export({
  format: 'pem',
  type: 'pkcs8',
});
const now = Date.now();
const registry = [{
  keyId,
  privateKeyPem,
  notBefore: new Date(now - 5 * 60_000).toISOString(),
  notAfter: new Date(now + 90 * 24 * 60 * 60_000).toISOString(),
}];
writeFileSync('offline-manifest-keys.json', `${JSON.stringify(registry)}\n`, {
  encoding: 'utf8',
  flag: 'wx',
  mode: 0o600,
});
process.stdout.write(`${keyId}\n`);
NODE
```

Map the printed ID to `OFFLINE_MANIFEST_ACTIVE_KEY_ID` and the exact file contents to `OFFLINE_MANIFEST_SIGNING_PRIVATE_KEYS_JSON`. In External Secrets mode, use two entries whose `secretKey` values exactly match those names; the chart routes them into the dedicated manifest target and rejects a missing mapping. Do not pass the JSON through `--set`, shell history, logs, CI output, or a general workload Secret. Materialize an environment file from the secret manager only on a protected host and run `bun run setup:check -- --mode production` before rollout.

Rotate in two reconciled rollouts. First add the new inactive key, reconcile the Secret, restart/roll out every API pod, and verify key discovery includes both keys. Then change the active ID, reconcile again, roll out every API pod, and verify newly downloaded manifests use the new ID. Secret-backed environment changes do not update a running pod. Retain each old key until its last manifest lifetime plus clock skew has elapsed. Browsers perform one cache-bypassing key refresh when a newly activated ID is not in their cached key set. The API derives the signed issuer from the exact external HTTPS `API_BASE_URL`; do not configure an internal service origin there. Preserve the V1 HMAC variables while supported native scanners still consume legacy manifests.

## Release order

1. Back up and verify restore readiness.
2. Run the release dry-run and documentation/OSS export gates.
3. Apply forward-compatible migrations using the approved migration identity.
4. Deploy API and worker with compatible Temporal workflow code.
5. Deploy admin, checkout, and docs.
6. Verify health, representative public/authenticated reads, checkout, workflow, webhook, and documentation routes.

## Rollback

Roll back application artifacts independently only while contract and migration compatibility permits it. Prefer a forward fix for destructive schema changes. Preserve documentation redirects so dashboard links remain valid across a docs rollback.

## Smoke checks

Verify `/health` for API and docs, worker readiness, a real published test event, authenticated context, and a test-safe checkout. A green homepage is not a complete deployment proof.

Continue with [observability configuration](/self-hosting/observability) before accepting the release.
