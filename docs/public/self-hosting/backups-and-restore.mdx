Backups are not complete until a restore rehearsal proves usable application state. Protect database data and required object-storage artifacts; document which ephemeral Redis/Temporal state is reconstructed and which durable Temporal persistence is protected by its own service plan.

## Backup

Run the repository's engine/object-storage backup procedures with encrypted destinations, least-privilege access, retention, and monitoring. Record timestamps and non-secret artifact identifiers.

Compact operators use `bun run compact:backup -- <directory>` and `bun run compact:restore -- <directory>`. The [Compact runbook](/self-hosting/compact) defines the artifact contents, checksum gate, and Temporal-volume boundary.

## Restore rehearsal

Restore into an isolated environment, run migrations only as required by the target commit, start API/worker/application processes, and verify tenant scope, a representative event/order, artifact download, workflow visibility, and health checks.

Measure recovery point and recovery time from actual rehearsal evidence. Do not publish invented RPO/RTO claims.

## Production recovery contract

Production backups must land in a failure domain independent from the primary services, use an identified encryption policy/key, and be signed with a manifest key stored separately from the artifacts. The scripts refuse to create a Production artifact unless `DR_BACKUP_DESTINATION_CLASS=independent`, `DR_BACKUP_ENCRYPTION`, `DR_MANIFEST_SIGNING_KEY`, `DR_MANIFEST_KEY_ID`, and `DR_SOURCE_RELEASE` are explicit.

Use `bun run dr:backup:production` with executable `DR_QUIESCE_COMMAND` and `DR_RESUME_COMMAND` controls. While writes and workers are quiesced, the command captures exactly one configured relational engine, owned object storage, and provider-executed Temporal checkpoint metadata under one recovery-point timestamp. `DR_TEMPORAL_CHECKPOINT_COMMAND` must return a verified immutable ID, namespace, and exact recovery point. Redis is explicitly reconstructible state, not a recovery source. The command always attempts to resume writes on failure.

Each artifact has a mandatory SHA-256 sidecar and a signed, versioned manifest binding its name, kind, size, checksum, recovery point, source release, encryption policy, and independent-destination class. A checksum without a valid manifest signature is insufficient. The Production bundle additionally requires `DR_BACKUP_PUBLISH_COMMAND`, `DR_BACKUP_RECEIPT_VERIFY_COMMAND`, and `DR_BACKUP_RETRIEVE_COMMAND`: the publisher must return an immutable provider receipt with different plaintext/ciphertext hashes and a provider signature, the provider-specific verifier must cryptographically validate that receipt, and retrieval must reproduce the signed plaintext exactly. Plaintext staging is then removed. Merely setting an “encrypted” environment label is not accepted as proof.

Backup output directories must be caller-owned and mode `0700` or stricter. Artifacts and sidecars are published exclusively at mode `0600`; existing paths, symlinks, inode substitution, concurrent publication, and partial publisher/retriever failures fail closed. Provider hooks execute with an explicit environment allowlist and never receive the manifest signing key.

## Staged restore and cutover

Never point a restore command at the active database or bucket. PostgreSQL and MySQL restores require `DR_ISOLATED_TARGET=1` and reject a non-empty target before mutation. PostgreSQL restores are transactional. Object restore requires a new `RESTORE_S3_BUCKET`, rejects traversal, links, devices, duplicate paths, and oversized expansion before extraction, mirrors with deletion semantics, and requires an exact post-copy diff.

Production MySQL recovery additionally requires verified-identity TLS, an authenticated short-lived provisioning receipt, `DR_MYSQL_TARGET_LEASE_COMMAND`, `DR_MYSQL_TARGET_LEASE_VERIFY_COMMAND`, and `DR_MYSQL_FAILED_RESTORE_CLEANUP_COMMAND`. The lease holder must atomically consume the provisioning nonce and hold or renew an exclusive provider lease bound to the artifact SHA-256, opaque restore target ID, server UUID, database, and unique attempt ID. Tixkit verifies the lease before import, periodically during import, after import, and before evidence; loss or expiry terminates the import and requires independently checked cleanup. The lease is released only after signed evidence or verified cleanup. A boolean “isolated” assertion or an empty-table query alone is not sufficient.

Production object recovery requires workload identity, metadata restore, a run-owned bucket-creation receipt, independent ownership verification, remote inventory reconciliation, and failed-bucket cleanup plus independent absence verification. Destructive cleanup is armed only after the ownership verifier binds the exact endpoint, bucket, and restore-run nonce. An existing bucket or a failure before ownership proof is never cleanup-authorized. Metadata hooks never receive the reconciliation output path; the inventory verifier returns its result on stdout and the parent exclusively writes mode-`0600` evidence binding the verifier hash and signed inventory.

Every restore requires an executable `DR_VERIFY_COMMAND`. This verifier must check tenant/event/order/ticket/payment invariants, owned object references and checksums, Temporal visibility/replay expectations, API and worker health, and representative checkout, webhook, check-in, and export behavior. When `DR_EVIDENCE_FILE` and `DR_INCIDENT_AT` are supplied, the restore signs evidence binding the artifact, target, source/target releases, verifier hash, recovery point, execution duration, measured RPO, and incident-to-recovery RTO. Future incident timestamps are rejected.

Use `bun run dr:restore:production` after the independent retrieval/decryption step. Supply opaque, non-secret `DR_DATABASE_TARGET_ID`, `DR_OBJECT_TARGET_ID`, and `DR_PRODUCTION_TARGET_ID` values; database URLs and credentials are deliberately excluded from evidence. Before any component mutation, a provider-authenticated target receipt must bind the physical application database, object store and Temporal persistence identities. `DR_PRODUCTION_TARGET_LEASE_COMMAND` must atomically acquire one renewable provider claim for that target triplet, while its independent verifier proves the live holder and fencing generation throughout restoration. Restore hooks receive the authenticated Temporal checkpoint through an anonymous read-only capability instead of the mutable extraction path; Linux seals the capability against writes, growth, shrinkage, and further seal changes. Hooks must consume that capability once per phase and keep any private parsed representation within the hook process. `DR_TEMPORAL_EVIDENCE_VERIFY_COMMAND` independently authenticates provider restore evidence and binds its immutable ID, namespace, workflow/run identity and recovery point to the backup checkpoint. The command safely extracts the outer bundle, rejects missing or extra artifacts, verifies every nested signature and shared recovery point/source release, restores all three isolated targets, and runs final live cross-store reconciliation. It writes signed component evidence plus an aggregate `production.json` whose hashes bind the publication receipt, exact retained object version, target claim, consequential adapters and all component results.

Provider claim completion is a separate durable transition after `production.json`. It must atomically validate the live holder and fencing generation, bind the exact aggregate-evidence hash, and return the same authenticated receipt on an identical retry. `DR_PRODUCTION_TARGET_CLAIM_QUARANTINE_COMMAND` quarantines an unfinished claim during controlled failure. If the provider committed completion but the local process stopped before writing or verifying its receipt, run `bun run dr:finalize-production-restore-claim` with the original evidence directory and provider completion/verifier commands; it verifies the signed aggregate and bound lease before recovering the receipt. Never retry restoration over an ambiguous active claim.

After review of the signed aggregate `production.json` and authenticated completed-claim receipt, use `bun run dr:promote-restored-target`. Promotion refuses component-only or unfinalized evidence. Operator-supplied commands atomically rebind the destination and verify the promoted runtime. If cutover or verification fails, the command restores and verifies the previous binding. Signed promotion evidence pins the completed-claim receipt and verifier, target, bundle, aggregate hash and fencing generation alongside every cutover/rollback command. The staged target and previous target remain available until the retention policy permits deletion.

## Migration rollback rehearsal

`bun run dr:migration-rehearsal` is run once for PostgreSQL and once for MySQL. Start from `infra/production/migration-rehearsal.env.example`, store the completed non-secret copy outside the repository, create canonical caller-owned backup/evidence directories with mode `0700`, and export the file with `set -a` while sourcing it. Each run requires source, empty forward-clone and empty rollback-clone URLs; distinct opaque target IDs; signed old/new release attestations; immutable staged migration/verifier artifacts; and a release-attested database identity command. Capture one UTC anchor immediately before the command and pass it as both `DR_RECOVERY_POINT_AT` and `DR_INCIDENT_AT`; an incident earlier than the signed backup recovery point is invalid. The identity command must authenticate the physical database identity, prove all three roles are distinct, show the source is non-empty, and return the same reconciliation digest after both restores. Load the signing key from an authorized secret broker only for the rehearsal process. The runner removes it, all other caller secrets, source authority and rollback authority from migration/verifier/database-tool children.

The rehearsal backs up the source, restores and verifies the forward clone, runs the real migration with a bounded deadline, verifies the new version, then restores and verifies a second old-version clone. Evidence binds a one-time run nonce, ordered phase timestamps, signed restore receipts, release attestations, exact executed snapshots, physical identities and measured RPO/RTO. For an intentional failure, set `DR_EXPECT_FORWARD_FAILURE=1`, provide a signed `DR_FAILURE_INJECTION_MANIFEST`, and choose an exact `DR_EXPECTED_MIGRATION_EXIT_CODE` from 1 through 123. The migration runner must answer the one-time challenge with the prescribed structured result. Generic failures, timeouts, missing markers and replayed receipts fail closed while restore-based rollback still runs. The canonical commands and variable contract are enforced by the `dr:*` scripts in the root package manifest and `.github/workflows/production-dr.yml`.

These commands make local and production-like drills reproducible. The repository safety suite proves fail-closed contracts with controlled adapters, including concurrent MySQL lease contention, object cleanup authorization, lease/checkpoint loss, and crashes before provider completion, after provider completion, and before local completion verification. The opt-in `bun run test:production-dr:integration` gate exercises digest-pinned MySQL 8.4/MinIO and Temporal 1.24/PostgreSQL 16 component recovery plus one real outer `production-backup.sh` → immutable independent publication → source destruction → `production-restore.sh` round trip. The outer proof migrates and seeds real Tixkit tenant/event/media state, restores distinct application and Temporal PostgreSQL systems plus MinIO, permits exactly one concurrent mutating winner, reconciles live application/media/workflow state, recovers the exact retained provider version after a newer overwrite, denies replay and wrong-key retrieval, and proves idempotent durable claim finalization. This is real local provider proof, not production-like Kubernetes, managed-provider, zone/dependency, upgrade/rollback, or EPYC RPO/RTO proof; those external gates remain unverified.
