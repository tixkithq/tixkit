Compact is the supported single-host profile for evaluation and smaller installations. It runs the API, worker, admin dashboard, checkout, migrations, seeded evaluation data, PostgreSQL, Redis, Temporal, Temporal UI, S3-compatible object storage, and an internal ClamAV malware scanner. It is not highly available and does not run MySQL alongside its default PostgreSQL database.

## Host envelope

Use a 64-bit Linux host or Docker Desktop with at least 4 CPU cores, 12 GiB of memory, and 30 GiB of free disk. ClamAV needs several GiB to load its signature engine and can briefly use more memory while reloading updated signatures. Building all application images is also resource-intensive; 8 cores, 16 GiB of memory, and 60 GiB of free disk is the recommended starting envelope. Measure your own event, checkout, workflow, media, and retention load before production use. Move to the Production profile when you need multiple hosts, independent scaling, managed backing services, availability guarantees, or formal disaster-recovery objectives.

## First start

From the repository root:

```bash
bun run compact:init
bun run compact:up
```

`compact:init` writes `infra/compact/.env` with mode `0600`, a deployment identity, project-scoped source-build image names, and unique persistent-service and Ed25519 portability signing keys. Only the API receives the bundle, payload and dry-run private keys plus cutover public trust needed by its current runtime routes; migration, seed, storage-init and worker containers do not receive those private keys. The generated cutover private key remains host-local for future source-side exchange tooling and is not injected into a container. Back up this file separately; it contains private keys and must not be committed or shared. External source-key registration and destination worker import trust are not configured by this bootstrap step. In the default source mode, `compact:up` builds the application images. It then applies idempotent migrations, creates the object bucket, seeds an evaluation organization and event, and waits for every service health condition.

The pinned ClamAV image includes a signature database for first start and keeps subsequent FreshClam updates in the `clamav-data` volume. ClamAV is reachable only on the internal Compose network; only the API receives its host, port, scanner-mode and bounded 30-second scan-deadline configuration. The first health transition can take six minutes or longer while the engine loads. FreshClam requires outbound HTTPS and DNS for current signatures and may be delayed by upstream availability or rate limits. A healthy service proves that the loaded database can scan; it does not prove that signatures are current when update access is unavailable. Upload completion fails closed while the scanner is unavailable or exceeds its deadline.

The source-build names are deliberately separate from the public release contract. To consume a published version instead of building the checkout, initialize with `--image-mode release --version <version>`:

```bash
bun run compact:init -- --image-mode release --version 1.2.3
bun run compact:up
```

Release mode validates the four stable `tixkit/<service>:<version>` references and pulls them without a local build. A protected release or operator may replace each generated `TIXKIT_*_IMAGE` value with its corresponding `tixkit/<service>@sha256:<digest>` reference from the release manifest. The current frontend images compile their API origin at build time, so release mode deliberately fails closed unless the default project and port layout is retained; it cannot be co-hosted with a second Compact release installation yet. Source mode is required for custom ports and isolated installations on one host. This constraint prevents a pulled admin or checkout image from silently routing to the wrong API. Environments created before image modes existed continue to use the historical default project and local build tags without rewriting their secrets.

The default endpoints are:

- checkout: `http://localhost:3000`
- admin: `http://localhost:3001`
- API readiness: `http://localhost:4000/ready`
- Temporal UI: `http://localhost:8080`
- MinIO console: `http://localhost:9001`

In source mode, edit the non-secret `*_PORT` values in `infra/compact/.env` before `compact:up` when a host port is already occupied. Frontend API URLs are baked into their images, so rerun `compact:up` after changing `API_PORT`. Release mode rejects any port change until published frontends support runtime API-origin configuration.

### Isolated installations on one operator host

Every Compact lifecycle command accepts `--env-file <path>` and `--project-name <name>`. The environment file records its Compose project name, so containers, networks and named volumes do not overlap. Use distinct host ports for installations that run at the same time:

```bash
bun run compact:init -- \
  --env-file ./compact-source.env \
  --project-name tixkit-compact-source
bun run compact:init -- \
  --env-file ./compact-destination.env \
  --project-name tixkit-compact-destination
```

Edit the destination `*_PORT` values before starting both projects. When changing `MINIO_API_PORT`, set `S3_PUBLIC_ENDPOINT` to the exact matching `http://localhost:<MINIO_API_PORT>` origin; validation rejects mismatches so browser-signed uploads cannot reach another local installation. Always pass the matching environment and project flags to `compact:up`, `compact:status`, `compact:logs`, `compact:backup`, `compact:restore`, `compact:upgrade` and `compact:uninstall`. Compact rejects a project-name override that does not match the owner recorded in the selected environment. Each project also receives distinct local application image tags, preventing one installation's frontend build and baked API URL from replacing another installation's restart image.

## Operate

```bash
bun run compact:status
bun run compact:restart
bun run compact:logs
bun run compact:logs -- api worker
```

`compact:restart` removes and recreates the profile containers without rebuilding images or deleting the five named data volumes. This reruns migrations, storage initialization and the idempotent seed before waiting for every long-running service to become healthy. Restarting the host or Docker also preserves the named volumes, including downloaded ClamAV signatures; use `compact:restart` afterward for the supported full-profile restart check.

From a fresh authoritative public clone on a host that meets the minimum envelope, retain a machine-readable lifecycle proof with:

```bash
bun run compact:prove -- \
  --ref refs/heads/main \
  --out /private/tmp/tixkit-compact-proof-$(date -u +%Y%m%dT%H%M%SZ)
```

The output directory must be new, outside the repository and beneath a real non-symlink parent. The proof command refuses a dirty, shallow, non-public or already initialized clone, and requires `HEAD` to equal the object currently advertised by the named authoritative public branch or version tag. Its v2 evidence records the remote ref/object, exact commit/tree, host and Docker envelope, all 14 service states, seed persistence, restart, backup/restore, live database/object fingerprints for every negative restore case, clean-file acceptance at the 50 MiB upload limit, EICAR rejection, scanner outage and recovery through the actual API scanner transport, Temporal dependency failure/recovery, upgrade, validation commands and a mode-`0600` transcript. Scanner probe output and daemon metadata are omitted; their bounded command records and checksummed boolean outcomes remain in the proof. The transcript fails closed if it contains generated credentials. A passing local artifact is still not hosted publication, high-availability, legal or Production-profile proof.

## Trust a portability source

On the source Compact host, write the public identity artifact:

```bash
bun run compact:portability-identity -- ./compact-source-identity.json
```

For an isolated non-default installation, pass its environment explicitly:

```bash
bun run compact:portability-identity -- \
  --env-file ./compact-source.env \
  ./compact-source-identity.json
```

The command prints the artifact's SHA-256. The JSON contains only the deployment identity and Ed25519 public keys, plus a self-signature proving possession of the advertised bundle key. Send the JSON and its printed SHA-256 to the destination over separate authenticated channels. The self-signature detects modification but does not establish trust by itself; the destination operator must verify the expected SHA-256 out of band.

On the destination Compact host, install trust for that exact source. Set the capacity to the number of bytes actually available to Tixkit-owned object storage, excluding the space needed for databases, logs, backups, and upgrades:

```bash
bun run compact:portability-trust -- \
  --env-file ./compact-destination.env \
  ./compact-source-identity.json \
  --sha256 <verified-sha256> \
  --available-storage-bytes <available-bytes>
bun run compact:up
```

The trust command verifies the checksum, strict artifact schema, bundle-key self-signature, distinct Ed25519 role keys, current API/data-schema pair, and different source/destination deployment identities and authorities. It then atomically adds only source public keys and destination compatibility policy to the mode-`0600` environment. The worker receives the resulting import trust; the API receives the source cutover public key. Source private keys never enter the artifact or destination. A destination has one explicitly selected import source at a time. Replacing it requires `--replace`, followed by `compact:up`; retain the verified artifact and checksum with the migration change record. Concurrent trust changes fail closed. No existing `infra/compact/.env.portability.lock` is removed automatically. If the trust process is forcibly terminated, verify from the recorded PID that no trust process is running before removing the lock manually.

## Back up and restore

```bash
bun run compact:backup -- ./backups/compact-$(date -u +%Y%m%dT%H%M%SZ)
bun run compact:restore -- ./backups/compact-20260711T120000Z
```

The backup quiesces the application and workflow tier, then captures the application database, both Temporal databases, and owned object storage as one logical snapshot. Its manifest records the Tixkit version, source commit, byte counts, and SHA-256 checksums. Restore verifies the exact artifact set, checksums, version, and archive entry safety, restores into temporary databases and a temporary bucket, and validates their required schemas before cutover. It retains rollback databases and objects until the complete profile is healthy. Keep backup directories and `infra/compact/.env` encrypted outside the host's failure domain. Compact Redis state and ClamAV signatures are reconstructible operational data and are not included in the logical backup; after loss of `clamav-data`, the pinned image provides its bundled database and FreshClam must regain update access before signature freshness can be claimed.

## Upgrade and uninstall

After checking out the reviewed target release:

```bash
bun run compact:upgrade
```

The command creates a checksummed pre-upgrade backup, pulls current base images, rebuilds the application images from the checked-out release, reapplies migrations, and waits for health. Test restore before upgrading important installations.

Remove containers while preserving data and secrets with `bun run compact:uninstall`. Destructive removal is explicit:

```bash
bun run compact:uninstall -- --volumes
```

The destructive form removes Compact volumes and its generated environment file. Verify an external backup first.
