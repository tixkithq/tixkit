Compact is the supported single-host profile for evaluation and smaller installations. It runs the API, worker, admin dashboard, checkout, migrations, seeded evaluation data, PostgreSQL, Redis, Temporal, Temporal UI, and S3-compatible object storage. It is not highly available and does not run MySQL alongside its default PostgreSQL database.

## Host envelope

Use a 64-bit Linux host or Docker Desktop with at least 4 CPU cores, 8 GiB of memory, and 30 GiB of free disk. Building all application images is resource-intensive; 8 cores, 16 GiB of memory, and 60 GiB of free disk is the recommended starting envelope. Measure your own event, checkout, workflow, media, and retention load before production use. Move to the Production profile when you need multiple hosts, independent scaling, managed backing services, availability guarantees, or formal disaster-recovery objectives.

## First start

From the repository root:

```bash
bun run compact:init
bun run compact:up
```

`compact:init` writes `infra/compact/.env` with mode `0600` and unique persistent-service and signing secrets. It refuses to overwrite an existing file. Back up this file separately; do not commit or share it. `compact:up` builds the application images, applies idempotent migrations, creates the object bucket, seeds an evaluation organization and event, and waits for every service health condition.

The default endpoints are:

- checkout: `http://localhost:3000`
- admin: `http://localhost:3001`
- API readiness: `http://localhost:4000/ready`
- Temporal UI: `http://localhost:8080`
- MinIO console: `http://localhost:9001`

Edit the non-secret `*_PORT` values in `infra/compact/.env` before `compact:up` when a host port is already occupied. Frontend API URLs are baked into their images, so rerun `compact:up` after changing `API_PORT`.

## Operate

```bash
bun run compact:status
bun run compact:logs
bun run compact:logs -- api worker
```

Restarting the host or Docker preserves the four named data volumes. Running `bun run compact:up` again rechecks migrations, storage initialization, seed idempotency, and service health.

## Back up and restore

```bash
bun run compact:backup -- ./backups/compact-$(date -u +%Y%m%dT%H%M%SZ)
bun run compact:restore -- ./backups/compact-20260711T120000Z
```

The backup quiesces the application and workflow tier, then captures the application database, both Temporal databases, and owned object storage as one logical snapshot. Its manifest records the Tixkit version, source commit, byte counts, and SHA-256 checksums. Restore verifies the exact artifact set, checksums, version, and archive entry safety, restores into temporary databases and a temporary bucket, and validates their required schemas before cutover. It retains rollback databases and objects until the complete profile is healthy. Keep backup directories and `infra/compact/.env` encrypted outside the host's failure domain. Compact Redis state is reconstructible and is not backed up.

## Upgrade and uninstall

After checking out the reviewed target release:

```bash
bun run compact:upgrade
```

The command creates a checksummed pre-upgrade backup, pulls current base images, rebuilds the application images from the checked-out release, reapplies migrations, and waits for health. Test restore before upgrading important installations.

Remove containers while preserving data and secrets with `bun run compact:uninstall`. Destructive removal is explicit:

```bash
bun run compact:uninstall -- --volumes
```

The destructive form removes Compact volumes and its generated environment file. Verify an external backup first.
