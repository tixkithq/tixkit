The Production profile is the high-availability Self-Hosted path. It requires Kubernetes 1.30 or newer so the scheduler enforces the chart's stable two-domain `minDomains` topology contract. It consumes immutable public images and requires external PostgreSQL or MySQL, Redis, Temporal, object storage, secrets, telemetry, and backup services. It does not install evaluation datastores.

## Compatibility contract

Pin one public Tixkit release manifest and keep its API image, worker image, migration image, admin image, checkout image, OpenAPI version, migration range, and Temporal workflow code together. The chart requires digest-addressed images. Validate PostgreSQL 16 or MySQL 8.4, Redis 7, a compatible Temporal 1.24+ service or Temporal Cloud namespace, and the target S3-compatible API in a staging cluster before production adoption. A provider claiming protocol compatibility is not proof; run the repository's database, Temporal replay, object, and provider failure suites.

Do not roll application images behind an incompatible schema or workflow deployment. Use the [upgrade runbook](/self-hosting/upgrades), and retain the prior public release manifest and restored target until post-cutover verification completes.

## Initial sizing tiers

These are load-test starting points, not capacity guarantees:

| Tier   | API                                | Worker                                        | Admin                      | Checkout                   | Starting use                         |
| ------ | ---------------------------------- | --------------------------------------------- | -------------------------- | -------------------------- | ------------------------------------ |
| Small  | 2 × 250m CPU / 512 MiB             | 2 × 250m / 512 MiB                            | 2 × 200m / 384 MiB         | 2 × 200m / 384 MiB         | Staging and smaller steady workloads |
| Medium | 3–6 × 500m / 1 GiB                 | 3–8 × 500m / 1 GiB                            | 2–4 × 250m / 512 MiB       | 3–8 × 300m / 512 MiB       | Multiple concurrent onsales          |
| Large  | Result of measured load/soak tests | Separate task queues and measured concurrency | Measured dashboard traffic | Measured burst concurrency | High-volume or event-day peaks       |

Keep at least two replicas, topology spreading, disruption budgets, bounded autoscaling, and enough cluster headroom to replace one failure domain. Size relational connections, Redis, Temporal task queues, object throughput, OTLP, and Pushgateway alongside pods. Run checkout/inventory concurrency, webhook replay, check-in sync, exports, and failure injection at the intended peak plus safety margin; record saturation and recovery, then set requests, limits, HPA bounds, and worker concurrency from that evidence.

## Installation controls

Start from `infra/helm/tixkit/values-production.yaml`. The chart fails when image digests, operator-selected network CIDRs, manual migration strategy, observability, or required external secret mappings are absent. For External Secrets, reconcile the secret, run `infra/scripts/run-helm-migration.sh`, and only then install or upgrade workloads. The migration runner uses a lock, unique Job, isolated egress policy, and current logs; it never reuses an old completed Job.

Production renders zero-unavailable rolling updates with a replacement surge, a readiness dwell, a bounded progress deadline, at least two replicas per workload, a disruption budget below the minimum replica count, and a hard topology-spread minimum of two zones. A digest change rolls the relevant workload; a chart-managed ConfigMap change changes the pod-template checksum and rolls all four workloads. After an external Secret value changes, explicitly restart and verify the affected workloads because the chart cannot hash provider-owned secret contents.

Run the production conformance harness first without disruption, then with its exact destructive acknowledgement. Use a dedicated production-like cluster and an operator-owned evidence directory:

```bash
EXPECTED_KUBE_CONTEXT=tixkit-production-proof \
NAMESPACE=tixkit \
RELEASE_NAME=tixkit \
DRILL_ID=preflight-2026-07-13 \
EVIDENCE_DIR=./artifacts/production-proof \
bun run iac:verify:production

EXPECTED_KUBE_CONTEXT=tixkit-production-proof \
NAMESPACE=tixkit \
RELEASE_NAME=tixkit \
DRILL_ID=pod-replacement-2026-07-13 \
EVIDENCE_DIR=./artifacts/production-proof \
PRODUCTION_DISRUPTION_ACK=evict-one-pod-per-component \
bun run iac:verify:production
```

The harness refuses a context mismatch or existing evidence file, verifies digest-pinned images, replica/readiness, HPA bounds, rollout bounds, disruption headroom, the live two-zone topology constraint, and Ready pod placement across distinct node zones. It binds cluster, namespace and Helm release identity, submits one policy eviction per workload only after the explicit acknowledgement, waits for a distinct Ready pod UID and fully observed deployment replacement, and writes before/after JSON without secret values. This is pod-replacement evidence only; it does not replace zone-loss, dependency, upgrade, rollback or cross-store DR drills.

Use the signed [Production cluster rehearsal contract](https://github.com/tixkithq/tixkit/blob/main/infra/production/README.md) for the remaining cluster drills. It supports exact `zone-loss`, `dependency-loss`, and `release-upgrade-rollback` modes, requires a drill-specific destructive acknowledgement and an owner-only independently reviewed expectations file, and compares the live cluster identity, thresholds, release manifest hashes and image maps, and all five adapter hashes before any adapter can execute. It pins operator adapter bytes and the private evidence-directory identity through publication, records functional-probe outage and recovery measurements, verifies rollback against live image and topology state, and publishes exclusive Ed25519-signed/checksummed evidence. Run dependency loss separately for the configured database, Redis, Temporal, and object storage. A valid local controlled-adapter result is implementation proof only; C-119 remains open until the contract runs on a reviewed production-like cluster and the independently expected proof verifies.

Before accepting the release, prove pod replacement, zone disruption, dependency loss, retry recovery, upgrade, application rollback, staged data restore, failed-cutover rollback, authenticated metrics, trace delivery, and alert routing. Record actual RPO/RTO from the [backup and restore runbook](/self-hosting/backups-and-restore). Until those drills pass in the operator's environment, the profile is configured but not production-proven.
