Use test-only attendee and buyer data. Never place a real payment credential into a test environment or documentation example.

## Confirm the payment mode

Use only the test-payment mode assigned to the environment. Confirm the payment-account status in workspace settings before checkout. A successful test order proves the configured test journey; it does not by itself prove that live payments, settlement, disputes, or refunds are ready.

## Complete the purchase

1. Open the published event in a private browser window.
2. Select one available test ticket or product.
3. Complete all required buyer, attendee, and consent fields with non-customer data.
4. Review quantity, fees, discounts, and total before confirming.
5. Complete the environment-appropriate payment step.

Do not refresh or submit repeatedly while confirmation is pending. The flow uses idempotency and durable processing, but duplicate user actions complicate diagnosis.

## Verify the order

Return to **Orders** in the admin dashboard. Find the new order and confirm its payment/order state, line items, attendee records, and total. If checkout showed success but no order appears, preserve the non-secret order/session identifier and use the environment's authorized diagnostics or support channel.

## Prepare downstream operations

Use the test order to practice [refund handling](/operators/orders/refunds) and [check-in](/operators/check-in). Refunds may have external side effects; use only the environment's documented test mode for rehearsal.
